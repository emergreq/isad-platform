## Что стало сложнее и что важно учитывать

1. Больше правил находится в PL/pgSQL. Их удобнее проверять централизованно, но разработчику теперь нужно читать и серверный JavaScript, и миграции базы.
2. Новая версия API требует миграцию 016. Простого копирования файлов без обновления базы недостаточно. При обновлении сайт остановлен, миграция применена, затем сайт запущен вновь.
3. Некоторые ошибки предметной области теперь возвращают HTTP 422 вместо прежнего 400. Интерфейс портала продолжает показывать сообщение ошибки; внешним интеграциям стоит учитывать новый статус.
4. Индексы добавлены, но ускорение на большой нагрузке не измерялось. Оснований заявлять, что весь сайт стал быстрее, пока нет.
5. Миграция допускает сохранение старых некорректных строк с уведомлением NOTICE. Поэтому проверена её применимость к копии именно вашей рабочей базы: непройденных ограничений не осталось.

## Найденная ошибка и исправление

**Приоритет P2, подтверждено воспроизведением.** В миграции 016 триггер project_members_capacity вызывался только BEFORE INSERT. Команда UPDATE project_members SET role_id=... могла перенести участника в уже заполненную роль. На временной базе в роли с capacity=1 удалось получить двух участников. Обычный интерфейс сейчас такого переноса не предоставляет, поэтому проблема касалась прямого SQL и будущих обработчиков переноса.

Локальная миграция `db/017_project_member_updates.sql`:

- вызывает проверку при INSERT и при UPDATE project_id, role_id, user_id;
- блокирует целевую роль, чтобы конкурирующие запросы не заняли одно место дважды;
- при обновлении исключает текущую строку участника из подсчёта: сохранение той же роли не требует дополнительного места;
- сохраняет проверку, что роль относится к выбранному проекту;
- не изменяет уже применённую миграцию 016.

Добавлены пять регрессионных сценариев: перенос в заполненную роль, обновление той же роли и замена user_id, чужой проект, допустимый перенос и два одновременных переноса на последнее место. Все прошли. У неудачного переноса исходное участие сохраняется.

Дополнительно проверялась конкурентная подача одинаковых активных заявок на зачёт. Существующий частичный уникальный индекс препятствует созданию дубля; эту область ошибкой не считаю.
